## 1. PRINCIPIOS NO NEGOCIABLES (LA CONSTITUCIÓN)

Antes de realizar cualquier acción técnica, debes leer y respetar la Constitución del proyecto ubicada en [02-DOCS/wiki/constitution.md](file:///home/victor/develop/AgenteIaDesarrolloCustomized/02-DOCS/wiki/constitution.md). Los principios cardinales son:

1. **La Evidencia Manda**: Un test que pasa o un código que compila solo demuestra que el software ejecuta; no demuestra que cumpla lo que el usuario pidió. Toda tarea completada debe adjuntar evidencia observada (salida de terminal, pruebas de integración, respuesta HTTP real).
2. **Puerta Humana (Human-in-the-Loop)**: Queda terminantemente prohibido comenzar a escribir código de implementación en tareas complejas sin que el usuario haya aprobado previamente la especificación en el carril ASDD.
3. **Fricción Proporcional al Riesgo**:
   - Cambios pequeños y acotados: Usar **FTD (Fast-Track Development)** con un único documento ágil.
   - Nuevos proyectos, módulos, bases de datos o arquitectura: Usar **ASDD (Agent Spec-Driven Development)** con desglose formal.
4. **Atribución Humana en Git**: La autoría de commits pertenece exclusivamente al desarrollador humano. Nunca agregues notas de autoría de IA (`Co-Authored-By: DeepSeek`, `Generated by AI`, etc.).
5. **Memoria Continua (RSC Brain / LLM Wiki)**: Nunca asumas que comienzas de cero. Consulta siempre [02-DOCS/wiki/index.md](file:///home/victor/develop/AgenteIaDesarrolloCustomized/02-DOCS/wiki/index.md) y [02-DOCS/wiki/decisions.md](file:///home/victor/develop/AgenteIaDesarrolloCustomized/02-DOCS/wiki/decisions.md) para conocer las decisiones previamente acordadas.

## 2. FLUJO INICIAL OBLIGATORIO: SELECCIÓN DE STACK TECNOLÓGICO

Si el usuario solicita crear una nueva aplicación y aún no se ha definido el stack tecnológico, **NO debes asumir un lenguaje ni framework por tu cuenta**. Debes ejecutar de inmediato la habilidad `skills/stack-advisor/SKILL.md` y guiar al usuario mediante el siguiente diálogo estructurado:

### Paso 1: Pregunta de Alcance Móvil
Preguntar al usuario si desea un enfoque **Multiplataforma** o **100% Nativo**:
- **Si elige Multiplataforma**: Presentar las opciones agrupadas:
  1. *Líderes generales*:
     - **Flutter** (Dart): Renderizado gráfico propio (Impeller), interfaz uniforme, alto rendimiento.
     - **React Native con Expo** (TypeScript): Ecosistema npm, facilidad para compartir código con web.
     - **Kotlin Multiplatform (KMP) + Compose Multiplatform** (Kotlin): Lógica compartida en Kotlin con UI nativa o compartida.
  2. *Ecosistema .NET / C#*:
     - **.NET MAUI** (C# / XAML): Marco oficial de Microsoft para iOS, Android, macOS y Windows desde una única base de código.
     - **.NET MAUI Blazor Hybrid**: Componentes web Blazor (Razor) dentro de contenedor nativo con acceso total a APIs y hardware del dispositivo.
     - **Uno Platform / Avalonia UI**: Renderizado píxel a píxel multiplataforma con WinUI y Fluent Design.
- **Si elige 100% Nativo**: Preguntar si desea:
  - **Solo Android**: Kotlin + Jetpack Compose.
  - **Solo iOS**: Swift + SwiftUI.
  - **Ambos por separado**: Android nativo (Kotlin) e iOS nativo (Swift) con equipos o módulos independientes.

### Paso 2: Presentación del Top 5 Móvil y Top 5 Backend
Exponer al usuario los 5 más recomendados en cada área y razonar la elección según su tipo de app:
- **Top 5 Móvil**: Flutter, React Native (Expo), .NET MAUI / Blazor Hybrid, Kotlin Multiplatform, Nativo Puro (Compose / SwiftUI).
- **Top 5 Backend**: ASP.NET Core Web API (máxima sinergia con .NET MAUI), Node.js / NestJS o Fastify (TypeScript), Python FastAPI, Go (Gin / Fiber), Supabase / PostgreSQL (BaaS relacional).

Una vez que el usuario elija, registra la decisión en [02-DOCS/wiki/decisions.md](file:///home/victor/develop/AgenteIaDesarrolloCustomized/02-DOCS/wiki/decisions.md) y procede con la arquitectura limpia correspondiente.

## 3. ELECCIÓN DE METODOLOGÍA (FTD VS ASDD)

Evalúa la petición del usuario:

| Criterio | Carril FTD (Fast-Track) | Carril ASDD (Spec-Driven) |
| :--- | :--- | :--- |
| **Cuándo usar** | Corrección de bugs, endpoints aislados, cambios de estilo UI, refactorizaciones locales. | Crear nueva app, añadir autenticación, diseñar base de datos, pagos, módulos completos. |
| **Documentación** | Un único archivo en `02-DOCS/wiki/ftd/<slug>.md`. | `02-DOCS/wiki/sdd/specs/`, `plans/` y `progress/`. |
| **Aprobación** | Verificación directa con evidencia de prueba. | El usuario DEBE aprobar explícitamente la especificación antes de escribir código. |
| **Habilidad** | `skills/ftd-runner/SKILL.md` | `skills/asdd-orchestrator/SKILL.md` |
